# Study guide: D1 (Requirements and conceptual model)

## Summary
D1 describes the miniworld of MyKungFuAcademy, a single academy (ADR-0002). It has 7 stakeholders, 31 functional requirements (FR-01 to FR-31), 9 quantified non-functional requirements and 17 business rules. The conceptual ER model is drawn in the course notation (lecture T4, Silberschatz; ADR-0008). It has 20 entity sets: 3 weak, and 4 lower-level entity sets in 2 specializations. It has 31 relationship sets, including the ternary *promotion*. Ten exploratory questions cross several entity sets and trace back to FRs.

## Key concepts in simple words
- **Entity set / relationship set.** An entity set is a rectangle with its attributes listed inside, and the primary key is underlined. A relationship set is a diamond. Its own attributes go in a rectangle linked by a dashed line.
- **Cardinality limits `l..h`.** They are written on the line between an entity set and a diamond. They say how many times **one entity** takes part in the relationship set: `0..*` means optional and many, `1..1` means exactly one. The lecture asks for this format in the projects.
- **Total vs. partial participation.** l ≥ 1 means total and is drawn as a double line. l = 0 means partial and is drawn as a single line.
- **Weak entity set.** It has no key of its own. It is identified by the owner's key plus a **discriminator**, which has a dashed underline. Example: *rank* = (discipline_id, rank_order). It is drawn as a double rectangle, and the identifying relationship set (*has_rank*) as a double diamond.
- **Attribute kinds.** A composite attribute has indented components (`name` → `first_name`, `last_name`). A multivalued attribute is written `{a}`; this model does not use one. A derived attribute ends in `()` (`age()` is derived from `birth_date`).
- **Specialization.** Hollow arrows point to the higher-level entity set. **Overlapping** uses one arrow per lower-level entity set (*person* → *student*, *instructor*). **Disjoint** uses a single joined arrow (*event* → *competition*, *challenge*). The **completeness constraint** is partial by default; "total" must be annotated, and both of ours are total.
- **Generalization** is the same structure built bottom-up. *person* exists because students and instructors shared name, email and birth date.
- **Redundant attributes.** An entity set never stores another entity set's key, because the relationship set already expresses the link. The key comes back only when the model is mapped to tables in D2.
- **Primary key of a relationship set.** M:N: the union of the participants' keys (*attends* = student + class). 1:N: the key of the "many" side (*sets* = goal_id). Identifying: the weak entity set's key.
- **FR vs. NFR.** An FR says *what* the system does: actor, action, condition, and it is testable pass/fail. An NFR says *how well*, measured in ms, %, or volume.

## Likely oral questions (with model answers)
1. **The lecture says ternary relationships are "rare and to avoid". Why is *promotion* ternary?** Two binary relationship sets (*student*-*rank* and *instructor*-*rank*) cannot tell *which* instructor promoted *which* student to that rank. The fact involves all three entity sets at once. Its key is {student, rank}. (ADR-0004)
2. **Read *student* `1..*` - *enrolled_in* - `0..*` *discipline*.** Every student is enrolled in at least one discipline, so the participation is total and drawn with a double line. A discipline may have zero students.
3. **Why is *person* → {student, instructor} overlapping with two arrows?** One person can be both: an instructor can also train. It is total because there are no other kinds of person. (ADR-0003)
4. **Why is *event* disjoint?** A competition is never a challenge. Their attributes and participation data differ. It is drawn as one joined arrow plus "total". (ADR-0005)
5. **What is the primary key of *rank*?** It is a weak entity set: (discipline_id, rank_order), the owner's key plus the discriminator.
6. **Why does *student* not have a `discipline_id` attribute?** It would be a redundant attribute. The link is the relationship set *enrolled_in* (lecture: "Redundant attributes").
7. **Where is "Student Belt" from the brief?** It is replaced by *promotion*. The current belt is derived as the highest `rank_order` promoted. (ADR-0004, ADR-0007)
8. **Why is *criterion* an entity set and not a multivalued attribute of *evaluation*?** It carries extra data (`max_score`). The lecture's rule: use an entity set when more information must be captured.
9. **Primary key of *scored_on* and of *sets*?** *scored_on* is M:N, so its key is (evaluation_id, criterion_id). *sets* is 1:N (one student, many goals), so its key is goal_id.
10. **Which business rules cannot be drawn in the ER diagram?** BR-04 and BR-06 (next rank only, months and classes), BR-08 (capacity) and BR-09 (overlapping classes). They are enforced in D2 with constraints and triggers.
11. **Could aggregation be used here?** It would be used if another relationship set had to refer to a *promotion* (for example, a certificate issued for a specific promotion). The current requirements do not need it.
12. **Why no ACADEMY entity set?** There is a single academy, so the entity set would always have one row. (ADR-0002)
13. **What goes to MongoDB, and why?** Technique media, wearable time series, free-form feedback, the social feed and analytics, because that data has a variable schema or a high volume. Identities and rules stay relational.

## Practical exercises
1. Add rooms to classes. Decide whether *room* is an entity set or an attribute, and draw the change with `l..h`.
2. Write the cardinality limits for "a class may have one substitute instructor".
3. A student may have several phone numbers. How do you draw it, and how does it map to tables?

<details><summary>Solutions</summary>

1. If rooms have their own data (capacity, equipment), *room* is an entity set: *class* `1..1` - *held_in* - `0..*` *room*, with a double line on the *class* side. Otherwise `room` is an attribute of *class*.
2. New relationship set *substitutes*: *class* `0..1`, *instructor* `0..*`. Both are single lines (partial).
3. Write the multivalued attribute `{phone}` inside *person*. In D2 it becomes a separate table `person_phone(person_id, phone)`.
</details>
